근거 관계 `SUPPORTED/REFUTED/INSUFFICIENT`와 주장 판정 5종은 별개다. 최종 주장 판정은 ‘근거로 확인됨·반박됨·검증 불충분·검토 필요·검증 대상 제외’, 종합 판정은 ‘주요 주장 확인·일부 사실·허위 주장 확인·맥락 왜곡 확인·검증 불충분·추가 검토 필요’다. 종합 판정이 동시에 성립할 때 우선순위/다중 표기, 핵심 주장 선정, 근거 강도 기준은 **TASK-013 미결정**이다.

음성 PoC도 최소한의 URL/인용 원문 검증과 유보 처리 없이 확정 판정을 만들지 않는 방향을 검토한다. 이는 기획 원칙의 단계 적용 제안이며 완료 수준은 TASK-002에서 합의한다. URL 입력·다국어·실시간·일괄/팀 기능은 확장 범위다.

사용자 기획서에서 요구한 기능을 아래 초안 목록으로 등록했다. 세부 인수 조건과 우선순위 검토는 TASK-002에서 진행한다. 업로드/전처리·작업/삭제·결과 UI는 기반 구현, 실제 AI와 시각/통합 기능은 미완료다. 개발 도구 설치를 제품 기능으로 집계하지 않는다.

## 3. 기능 상세 양식

기능마다 다음 항목을 채운다.

1. 목적과 사용 시나리오: 행위자, 시작 조건, 완료 결과.
2. 입력·출력: 필수/선택 값, 형식, 길이, 경계값, 표시 규칙.
3. 권한: 누가 어떤 자원에 어떤 동작을 할 수 있는지.
4. 업무 규칙: 상태 변경 조건, 불변 조건, 중복 요청·동시 변경 처리.
5. 실패 처리: 유효성 오류, 권한 거부, 데이터 없음, 외부 장애, 재시도.
6. 저장 및 연동: `DB-`, `API-`, `UI-`, `BE-` ID 연결 또는 해당 없음 사유.
7. 인수 조건: 전제(Given)·행동(When)·관찰 가능한 결과(Then).
8. 검증: 정상/오류/권한/경계 사례와 테스트 경로, 실행 결과.

아직 채택하지 않은 기능을 예시만 보고 자동으로 구현하지 않는다.

## 4. 인수 조건 작성 규칙

‘정상 동작’, ‘빠르게’, ‘안전하게’처럼 단독으로 판정할 수 없는 문구를 피한다. 화면 변화, 상태값, 응답 코드, 저장 결과 등 관찰 가능한 결과를 쓴다. 접근 제한 기능은 허용 사례와 거부 사례를 모두 정의한다. AI 결과를 쓰는 기능은 불확실성 표시·근거 노출·잘못된 결과의 수정 경로를 별도로 정한다.

원문 근거 강도는 높음(직접 근거·핵심 정보 일치·중요 모순 해소), 보통(관련 근거는 있으나 독립성/직접성 한계), 낮음(근거 부족/핵심 불확실성)이다. 판정과 별도로 표시하며 진실 확률로 변환하지 않는다.

가상 예시의 음성 50%·자막 500%·근거 5%는 의미 비교와 프로그램 검사 및 내부/외부 불일치를 설명하는 사례다. 인식 오류와 실제 원문의 오류를 구분하고 검증된 동일 기간·지역·통계 항목 없이 반박으로 확정하지 않는다.

## 7. 현재 구현과 인수 범위 (2026-10-16)

- FEAT-001: 스트리밍 파일당 100 MiB, MP4/MP3/WAV 확장자 검사. Worker는 실제 컨테이너·오디오 존재·180초·전체 디코딩을 검사한 뒤 외부 처리 단계로 간다. 사전 검사 실패 시 유료 호출은 없다.
