## 1. 시작점과 현재 상태

초기 문서 작성 당시 제품 코드·제품 DB·제품 API가 없었다. 현재는 2026-10-16 첫 개발용 PoC 기반 구현이 추가됐으며 최신 상태는 10/99의 구현 기록을 따른다. 개발 도구 설정과 이 문서 세트가 준비되어 있다. 사용자 제공 [FactLens AI 기획서 원문](../references/FactLens_AI_기획서_원문.md)를 기획 기준으로 사용한다. 원문은 제안·개발 계획 초안이며 제안 스택과 평가 목표를 구현 사실로 취급하지 않는다. 상세 검토는 01~09, 후속 작업은 99에 연결한다. 현재 재개 지점은 [해야 할 일](99_해야할일..md)의 `TASK-016`(실제 AI 연결)이다. 유료 예산은 `TASK-001`, 평가 전 프로토콜은 `TASK-014`, 공개 전 보호는 `TASK-015/017`에서 다룬다.

이 문서들은 실제 제품 설계를 채우기 위한 초안이다. 작성 항목이 있다는 사실을 설계 승인·구현 완료·배포 완료로 해석하지 않는다.

## 3. 상태와 근거 표기

문서 상태와 작업 상태는 별도로 기록한다.

| 구분 | 허용 값 | 의미 |
|---|---|---|
| 문서 | 초안 / 검토 중 / 승인 / 변경 필요 | 설계 내용의 검토 상태 |
| 구현 | 미구현 / 진행 중 / 구현됨 | 코드 존재 여부 |
| 검증 | 미실행 / 통과 / 실패 / 일부 검증 / 해당 없음 | 실행한 검사의 결과 |
| 작업 | 대기 / 진행 중 / 차단 / 완료 / 취소 | 실행 항목의 진행 상태 |

- 확인된 사실에는 파일 경로, 명령 결과 또는 사용자 결정 기록을 붙인다.
- 미정은 `미결정: 무엇을 / 왜 / 어떤 작업에서 결정하는지`로 쓴다.
- 제안은 `제안 — 미승인`으로 구분한다. 승인 여부를 추측하지 않는다.
- 검증 기록은 실행일·대상·명령/방법·결과·제한을 포함한다. 이전 환경 검증은 과거 기록임을 표시한다.
- 비밀값, 인증 토큰, 실제 개인정보를 문서·예제·로그에 넣지 않는다.

| 접두사 | 기록 위치 | 추적 대상 |
|---|---|---|
| `DEC-` | 01 | 제품·기술 결정 |
| `FEAT-` | 02 | 기능 |
| `DB-` | 03 | 데이터 모델 |
| `API-` | 04 | API 계약 |
| `FLOW-` | 05 | 업무 흐름 |
| `UI-` | 06 | 화면과 클라이언트 모듈 |
| `BE-` | 07 | 서버 모듈 |
| `OPS-` | 08 | 환경·운영 절차 |
| `RISK-` | 09 | 위험과 개선 |
| `FILE-` | 10 | 파일 점검 |

각 접두사에서 세 자리 순번을 발급하고 삭제한 번호를 재사용하지 않는다. 표 양식의 `NNN`은 미발급 자리 표시자다. 실제 항목으로 집계하지 않는다. 필요한 항목만 생성하며, 한 기능의 ID를 모든 문서에서 유지한다.

추적 방향: `TASK → FEAT → FLOW → DB/API → UI/BE → 검증 → FILE`. 저장이 필요 없는 기능의 DB 등은 이유와 함께 `해당 없음`으로 기록한다.

## 5. Superpowers 작업 절차

1. 작업 시작: 프로젝트 가이드의 공통 작업 지침(`AGENTS.md`)을 먼저 읽은 뒤 `00 → 99 → 관련 설계 문서 → 10` 순서로 읽고 실제 파일을 확인한다.
2. 목적·사용자·성공 조건이 빠졌다면 `brainstorming`으로 필요한 질문을 좁힌다. 문서 양식 작성과 제품 결정 승인을 구분한다.
3. 제품 설계는 작업 크기에 맞게 Superpowers 절차를 적용한다. 큰 설계는 `01`~`07`의 해당 문서에 작성한다. 같은 내용을 별도 spec에 복제하지 말고 관련 절을 참조한다. 필요한 설계 검토·승인 기록은 `01`에 남긴다.
4. 여러 단계의 구현 계획이 필요하면 승인된 설계를 기준으로 `writing-plans`를 사용한다. 상세 계획이 별도 파일이면 `99`에서 링크하고 요약 상태만 유지한다.
5. 구현 방식은 사용자 지시와 사용 가능한 도구에 맞춘다. 병렬 에이전트나 worktree를 문서만으로 자동 허용하지 않는다. 클라우드에서는 기존 격리 체크아웃을 사용한다.
6. 기능/버그 변경은 적용 가능한 `test-driven-development`, 실패 조사는 `systematic-debugging`을 사용한다. 문서만 바꾼 작업은 링크·구조·내용 일관성을 확인한다.
7. 완료 전 `verification-before-completion`으로 실제 근거를 확인한다. 필요한 코드 리뷰를 수행하고, 프로젝트 가이드 세트 중 영향받은 설계 문서·`09`·`10`·`99`와 `AGENTS.md`를 함께 갱신한다. 지침 변경이 없어도 `AGENTS.md`의 최근 작업 기록은 갱신한다.

이미 승인된 범위의 문서 정리·오탈자 수정마다 승인을 새로 요구하지 않는다. 새로운 제품 선택이나 범위 변경이 생겼을 때 그 결정에 필요한 검토를 진행한다.

## 8. 실제 작업 진행표

문서 번호는 분류이며 반드시 01부터 10까지 한 번씩 끝내야 한다는 의미가 아니다. 한 기능 단위로 필요한 문서를 오가고 변경 영향표를 적용한다.

| 단계 | 주 문서 | 수행 내용 | 다음 단계 조건 |
|---|---|---|---|
| 착수 | AGENTS → 00 → 99 → 10 | 지침·범위·현재 파일·검증 상태 확인 | 수행 TASK와 변경 범위가 분명함 |
| 범위 설계 | 01 | 목적·사용자·MVP·대안·결정 근거 | 관련 범위와 성공 조건 검토 |
| 동작 설계 | 02 ↔ 05, 09 | 기능·인수 조건·상태·실패/복구·위험 | 정상/오류/권한 결과를 판단할 수 있음 |
| 계약 설계 | 03 ↔ 04 ↔ 06 ↔ 07 | 데이터·API·화면·서버 경계 연결 | 필요한 계약과 기술 선택이 검토됨 |

| 구현/검증 | 06·07·08·10 | 필요한 코드와 테스트, 실제 실행 확인 | 인수 조건별 결과·제한 확보 |

### Superpowers 적용 방법

- 요구사항·새 기능·구조 설계: `brainstorming`. 기존 목적을 반복 질문하지 않고 이번 선택에 필요한 정보만 정리한다.
- 여러 단계의 구현: 설계 검토 후 `writing-plans`. 상세 계획을 별도 파일에 작성하면 99에서 연결하고 내용은 중복 관리하지 않는다.
- 직접 구현: `executing-plans`; 사용자나 적용 지침이 병렬 에이전트 작업을 요청한 경우에만 해당 병렬 절차를 선택한다.
- 기능/버그: 적용 가능한 `test-driven-development`; 실패 원인 조사: `systematic-debugging`.
- 완료 주장 전: `verification-before-completion`; 주요 구현의 검토에는 `requesting-code-review`를 적용한다.
- 이번 요청은 기존 문서 체계 정비다. 제품 구조·스택을 새로 확정하는 작업과 구분하며 제품 코드나 제품 의존성을 생성하지 않는다.

### 변경 기록 공통 양식

각 문서의 변경이 발생하면 해당 TASK에 다음을 남긴다. 동일 검증 로그는 10에 한 번 기록하고 나머지 문서는 참조한다.

| 일자 | TASK/관련 ID | 변경 이유·범위 | 결정 상태/근거 | 검증 기록 | 남은 일 |
|---|---|---|---|---|---|
| 실제 실행일 (양식) | 발급된 ID | 관찰 가능한 변경 | 확정/제안/미결정 | 10의 근거 또는 미실행 | 다음 TASK |

### 현재 재개 지점

첫 구현 설계(01 §9)와 구현 계획에 대한 사용자 진행 지시로 개발용 기반을 구현했다. 01 §7은 초기 추천 이력이고 현재 개발 기준은 §9~10이다. TASK-016에서 제공자·모델·가격/예산을 결정해 실제 분석을 연결한다. 새 운영 권한이나 유료 호출은 기존 구현 승인과 구분한다.
